## 二、实验背景

上一次实验课完成了初步需求讨论，本次实验将初步设想转化为可执行的软件工程方案。上学期 iChat Pro 已经实现账号、联系人、私聊、群聊、WebSocket、端到端加密、文件传输和设置中心等基础功能，因此本学期不以重复展示旧功能为主要成果。

本学期新增目标为：

1. 将现有系统升级为可安装的 Windows App 和 Android App；
2. 将系统部署到公网云服务器，实现不同设备和网络间的真实聊天；
3. 强化 E2EE、多设备和弱网可靠通信；
4. 建立黑盒、白盒、安全、性能和兼容性组成的产业级测试体系；
5. 使用 GitHub、CI/CD 和 AI 辅助工具贯通需求、开发、测试和交付过程。

### 5.3 Windows 与 Android 产品化

- Windows 端应形成可安装、启动、卸载的 `.exe` 应用；
- Android 端应形成可安装 APK，完成触屏、返回键、权限和生命周期适配；
- Windows、Android 和 Web 使用同一云端账号和业务数据；
- 三端应能够双向发送消息、同步状态和传输支持的加密文件；
- 客户端应提供连接状态、断线提示和自动重连；
- 私钥和登录凭据不得明文写入普通配置或日志。

### 5.4 公网云部署

- 使用公网域名、HTTPS 和 WSS；
- 使用 Nginx 与正式 Django ASGI 服务；
- 正式数据库由 SQLite 升级为 PostgreSQL；
- WebSocket Channel Layer 使用 Redis；
- 文件存储必须持久化；
- 建立环境隔离、秘密管理、日志、监控、备份、恢复和回滚流程。

### 5.5 E2EE 与可靠通信

- 客户端使用 ECDH、HKDF、AES-GCM 等机制完成加解密；
- 服务端不保存消息明文、文件明文、私钥或文件密钥明文；
- 私聊保存接收者密文和发送者独立密文副本；
- 群聊为每个有效成员保存独立密文；
- 使用客户端消息 ID 保证重试幂等；
- 支持发送中、已发送、已送达、已读和失败状态；
- 支持网络恢复后的自动重连和遗漏消息补取；
- 密钥变化不得自动继承旧密钥的可信状态；
- 多设备能力采用独立设备标识、设备密钥和设备撤销策略逐步实现。

### 5.6 产业级测试

- 黑盒测试：等价类、边界值、判定表、状态迁移、场景法和错误推测；
- 白盒测试：语句、分支、条件、基本路径、循环和异常路径；
- 专项测试：HTTP、WebSocket、E2EE、安全、性能、稳定性、弱网和兼容性；
- 客户端测试：Windows 安装/E2E、Android 权限/UI/生命周期；
- 运维测试：部署冒烟、健康检查、备份恢复和回滚；
- 质量目标：核心后端语句覆盖率目标 85%，分支覆盖率目标 75%，高风险逻辑目标 90%。

### 5.7 非功能需求与验收口径

| 类别 | 主要要求 | 验收方式 |
| --- | --- | --- |
| 可用性 | 三端提供一致的核心聊天流程，断线和失败状态清晰可见 | 跨端场景测试、用户操作检查 |
| 性能 | 常规负载下消息交互无明显卡顿，并形成并发测试基线 | Locust/k6 报告、服务监控数据 |
| 安全性 | HTTPS/WSS、最小权限、密钥不出端、无明文敏感日志 | 代码审查、ZAP/Bandit/依赖扫描、协议测试 |
| 可靠性 | 重连、重试、幂等、离线补取和消息状态可验证 | 弱网、断网、重复请求和恢复测试 |
| 兼容性 | 支持课程约定的 Windows、Android 和主流浏览器版本 | 真机/虚拟机兼容性矩阵 |
| 可维护性 | 任务、代码、测试和缺陷可追踪，配置与环境分离 | Issue/PR/CI 记录审查 |
| 可恢复性 | 数据库和文件可备份恢复，发布失败可以回滚 | 恢复演练与回滚演练 |

### 5.8 需求亮点

1. **从 Web 原型走向真实产品**：形成 Windows 安装包、Android APK 和公网服务，而不是只在开发机演示。
2. **跨网络真实聊天**：不同设备通过 HTTPS/WSS 连接云端，验证消息和文件的真实收发。
3. **端到端加密**：服务端只中转和保存密文，重点验证密钥边界、多设备和成员变化场景。
4. **可靠通信**：针对重连、重试、幂等、离线补取和状态同步建立明确需求。
5. **产业级测试**：同时覆盖黑盒、白盒、接口、E2EE、安全、性能、兼容性和运维测试。
6. **AI 可审计实践**：记录 AI 输出、人工修改和真实验证，避免把 AI 生成内容直接当作成果。

## 六、软件工程全链路

### 6.1 总体流程

```text
需求分析与评审
      ↓
需求编号、优先级与验收标准
      ↓
GitHub Issue 任务拆解
      ↓
功能/测试分支与代码提交
      ↓
Pull Request 与非作者评审
      ↓
静态检查、自动化测试与覆盖率
      ↓
缺陷登记、修复与回归测试
      ↓
Windows/Android 构建与测试环境部署
      ↓
云端冒烟、发布审批与回滚准备
      ↓
实验报告、测试报告与演示证据
```

### 6.2 需求到 Issue

完整需求使用 `NEW-*`、`FR-*` 和 `NFR-*` 编号。任务按两套序列管理：

- 开发与工程任务：`P4 T01–P4 T54`；
- 测试任务：`P4 Test T01–P4 Test T24`。

当前已经在 GitHub 建立 78 个 Phase 4 Issues。每个 Issue 包含所属工作域、优先级、前置依赖、交付物和验收标准；本报告已完成四名成员的责任划分，后续将分工同步到 GitHub Assignee。

[查看 Phase 4 Issues](https://github.com/HeanX/iChat_Pro/issues?q=is%3Aissue%20label%3Aphase-4)

### 6.3 Issue 到代码

每个开发或测试任务原则上建立独立分支：

```text
feature/p4-t15-windows-package
feature/p4-t24-android-build
fix/p4-t32-message-idempotency
test/p4-test-t13-websocket
docs/p4-t54-final-materials
```

提交信息中引用 P4 Issue 编号，例如：

```text
feat(android): build initial APK [P4 T24]
fix(realtime): prevent duplicate resend [P4 T32]
test(e2ee): add cross-platform vectors [P4 Test T06]
```

### 6.4 代码到评审

代码通过 Pull Request 合并。PR 至少说明：

- 关联 Issue；
- 修改目的和主要变更；
- 测试方法与测试结果；
- 界面或日志证据；
- 风险、兼容性和回滚方式。

原则上由一名非作者成员完成评审。E2EE、安全、权限、数据库迁移和部署配置等高风险改动应至少由开发和测试两个角色共同检查。

### 6.5 评审到测试

PR 合并前执行适用检查：

1. Django 系统检查；
2. migrations 一致性检查；
3. Python 后端测试；
4. JavaScript E2EE 测试；
5. 后续新增的格式、静态分析、覆盖率和依赖安全检查；
6. 对客户端或部署改动执行对应冒烟测试。

### 6.6 测试到缺陷闭环

缺陷使用 GitHub Issue 或缺陷记录表管理，内容必须包括：

- 关联需求和测试用例；
- 测试环境与前置条件；
- 复现步骤；
- 预期结果和实际结果；
- 严重程度和优先级；
- 截图、日志或录屏；
- 修复提交；
- 复测和回归结论。

### 6.7 发布与交付

发布流程分为测试环境和生产环境。测试环境完成自动部署和冒烟后，正式环境再进行人工审批。发布失败时按回滚文档恢复最近稳定版本，数据库变更必须具备向前兼容或恢复方案。

## 八、代码管理工作介绍

### 8.1 源代码管理

- Git：本地版本、分支和提交管理；
- GitHub：远程仓库、Issues、Pull Requests 和 Actions；
- `main`：保持可运行、可测试的主分支；
- `.gitignore`：排除虚拟环境、依赖、数据库、媒体、缓存和本地配置。

### 8.2 当前自动化基础

仓库当前的 GitHub Actions 工作流在推送到 `main` 和 Pull Request 时执行：

```text
安装 Python 3.13
→ 安装 requirements.txt
→ python manage.py check
→ python manage.py makemigrations --check --dry-run
→ python manage.py test
```

该流程是本学期 CI/CD 的起点，后续逐步加入格式检查、覆盖率、E2EE 测试、安全扫描、客户端构建和部署冒烟。

### 8.3 编码规范

#### Python 与 Django

- 遵循 PEP 8；变量和函数使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`；
- 导入按标准库、第三方库、项目模块分组，禁止无必要的通配符导入；
- View、Consumer、Service 和 Model 职责清晰，复杂业务逻辑不堆积在视图层；
- 数据模型变更必须提交 migration，并执行迁移一致性检查；
- 对象级操作必须检查当前用户权限，不能只依赖前端隐藏按钮；
- 涉及多表写入、消息状态和关键安全操作时按需使用事务；
- ORM 查询避免明显的 N+1 问题，异常响应不得泄露敏感信息。

#### JavaScript 与客户端

- 默认使用 `const`，确需重新赋值时使用 `let`，不使用 `var`；
- 变量和函数使用 `camelCase`，类或组件使用 `PascalCase`；
- 网络、WebSocket、加解密和本地存储操作必须处理失败、超时和重试；
- 不可信文本进入 DOM 前必须安全转义；
- Windows、Android 和 Web 保持协议字段一致，协议变化同步更新兼容性测试；
- 日志不得输出消息明文、密钥材料、密码或完整身份凭据。

#### 通用与安全规范

- 文件统一使用 UTF-8，命名表达实际业务含义；
- 密码、Token、私钥和生产配置通过环境变量或秘密管理服务注入；
- 上传文件检查扩展名、MIME、大小和存储路径；
- 所有敏感接口验证身份、权限、请求方法、输入长度和类型；
- 调试输出、数据库、媒体文件、缓存和个人环境配置不得进入正式提交。

### 8.4 分支与提交规范

| 类型 | 命名示例 | 用途 |
| --- | --- | --- |
| 功能分支 | `feature/p4-t14-windows-shell` | 新功能开发 |
| 测试分支 | `test/p4-test-t08-offline-replay` | 测试代码和测试环境 |
| 修复分支 | `fix/p4-t32-message-idempotency` | 缺陷修复 |
| 文档分支 | `docs/p4-t54-final-materials` | 文档与过程资产 |

提交信息采用“类型 + 简述 + Issue 编号”，例如：

```text
feat: add Windows reconnect indicator (P4 T18)
fix: reject unauthorized group message request (P4 T34)
test: cover offline message replay (P4 Test T08)
docs: update cloud deployment criteria (P4 T05)
```

常用类型为 `feat`、`fix`、`test`、`docs`、`refactor`、`chore` 和 `ci`。每次提交保持小而完整，不混入无关格式化和个人文件。

### 8.5 Pull Request 与完成定义

PR 必须写明关联 Issue、改动边界、测试方法、测试结果、风险和回滚方式；涉及界面时提供截图，涉及协议、数据库或配置时说明兼容性与部署步骤。

任务只有满足以下条件才可标记完成：

1. 验收标准全部满足；
2. 代码、配置、迁移和文档已经提交；
3. 相关自动化测试通过，人工测试有证据；
4. 非作者成员完成评审，阻断意见已经处理；
5. 不存在未说明的严重回归和高危安全问题；
6. 可以从需求追溯到 Issue、PR、测试和结果；
7. 部署类改动提供升级、兼容和回滚说明。

### 9.3 测试方法与层级

### 9.4 测试证据与准入规则

每次测试记录提交 SHA、环境、用例范围、执行人、时间、通过/失败/阻塞数量、日志和证据链接。测试数据使用构造数据，不公开真实聊天内容和密钥。

PR 合并前，相关自动化检查必须通过；发布前不得存在阻断级缺陷，严重缺陷必须修复或形成书面风险处置。失败用例不得通过删除测试、弱化断言或篡改数据规避。
