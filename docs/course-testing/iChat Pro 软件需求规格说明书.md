## 1. 引言

### 1.1 编写目的

本文档完整描述 iChat Pro 的系统范围、用户角色、功能需求、界面需求、数据需求、外部接口、非功能需求、业务规则和验收原则。上学期已经实现的账号、联系人、聊天、端到端加密、文件传输和设置等能力在本文档中作为“继承功能基线”，用于保证兼容性和回归质量。

继承自上学期软件工程学的课程设计，本学期我们在原有课程设计的基础上继续完善，目标的建设内容**是 Windows/Android 客户端产品化、公网云部署、跨设备真实聊天和产业级测试体系**。

本文档明确区分“既有功能”和“本学期新增需求”。课程验收不得将旧功能的简单复现视为主要创新成果，也不得将界面占位或计划能力描述为已经完成。

### 1.2 项目名称

iChat Pro——基于端到端加密的轻量级即时通信系统。

### 1.3 项目背景

即时通信系统需要同时满足易用性、实时性、数据隔离和隐私保护要求。传统服务端明文存储消息的方式会扩大数据泄露风险。iChat Pro 以课程项目规模实现账号、联系人、私聊、群聊、实时消息、文件传输及设置管理等能力，并通过浏览器端加密降低服务端接触聊天明文和文件明文的机会。

本学期将原有项目继续用于软件测试实践。项目目标不仅是展示功能，还要以可验证的需求为起点，形成“需求—代码—测试用例—缺陷—修复—回归—报告”的完整证据链。

### 1.4 术语与缩写

| 术语 | 含义 |
| --- | --- |
| E2EE | End-to-End Encryption，端到端加密 |
| WebSocket | 浏览器和服务端之间的全双工实时通信协议 |
| 密文 | 经客户端加密后、服务端不可直接读取的消息或文件内容 |
| 会话 | 私聊或群聊的逻辑容器 |
| 会话成员 | 用户与会话之间的成员关系，包含角色、未读数、静音等状态 |
| 密钥指纹 | 用于识别用户公钥版本的摘要标识 |
| Mock Provider | 无外部模型服务时返回模拟结果的 AI 服务实现 |
| HTTP fallback | WebSocket 不可用时使用 HTTP 完成消息发送的备用通道 |
| P0/P1/P2 | 高、中、低需求优先级 |

## 2. 系统总体说明

### 2.1 产品定位

iChat Pro 本学期定位为可真实安装、真实联网、真实跨设备通信，并具有完整质量保障体系的即时通信产品原型。系统继续复用现有 Django 和 Web 技术，但必须从本地演示模式升级为 Windows、Android 和浏览器共享云端服务的产品形态。

现有 SQLite、本地 Channel Layer 和开发服务器仅用于开发或单元测试，不作为公网正式部署方案。正式环境应采用 PostgreSQL、Redis、安全 ASGI 服务、HTTPS/WSS 和持久化文件存储。

### 2.2 系统目标

1. 将现有 Electron 原型升级为可安装、可运行、可卸载的 Windows App。
2. 基于现有 Web 能力提供可安装的 Android App，并完成移动端适配。
3. 将系统部署到公网云服务器，使不同地点和网络中的真实设备能够通信。
4. 使用 PostgreSQL、Redis、HTTPS/WSS 和持久化文件存储形成生产化基础架构。
5. 强化断线重连、消息幂等、状态同步和遗漏消息补取等可靠通信能力。
6. 在跨设备环境中明确设备身份、密钥保存、密钥变更和消息分发策略。
7. 保持现有账号、联系人、私聊、群聊、E2EE、文件和设置功能兼容可用。
8. 建立黑盒、白盒、接口、UI、安全、性能、兼容性和可靠性测试体系。
9. 建立自动化测试、覆盖率、依赖扫描、构建和部署组成的 CI/CD 质量门禁。
10. 形成需求、任务、代码、测试、缺陷、修复和回归完整可追溯链路。

### 2.3 技术架构

```text
浏览器 / Electron
  ├─ Django Templates + HTML/CSS/JavaScript
  ├─ Web Crypto API（消息和文件客户端加解密）
  ├─ HTTP/JSON（页面、接口、上传下载、备用发送）
  └─ WebSocket（实时消息、状态和事件）
                ↓
Django + Django Channels
  ├─ accounts：账号、资料、联系人、设置和密钥信任
  ├─ chat：会话、消息、群组、文件、搜索和 AI Assistant
  └─ SQLite：用户、关系、密文、状态和配置数据
```

### 2.4 用户角色

| 角色 | 权限与主要目标 |
| --- | --- |
| 访客 | 注册、登录；不能访问联系人、会话及用户私有数据 |
| 普通用户 | 管理资料和联系人，参与私聊/群聊，管理个人设置和消息 |
| 群成员 | 接收群消息、发送消息、查看有效成员和群信息 |
| 群管理员 | 审核邀请、管理成员、维护群公告和群设置 |
| 群主 | 拥有群最高管理权限，可转让群主或解散群聊 |
| 系统管理员 | 使用 Django 管理后台管理基础数据并记录管理操作 |

### 2.5 运行环境与约束

- Python 3.13 及 Django 6.0 系列运行环境。
- Django Channels 提供 ASGI 和 WebSocket 支持。
- 默认使用 SQLite，开发环境可使用内存 Channel Layer，配置后可使用 Redis。
- Web 前端依赖现代浏览器的 JavaScript、WebSocket 和 Web Crypto API。
- Electron 仅作为桌面外壳，不实现独立业务逻辑。
- 项目不是完整前后端分离架构，页面由 Django Templates 渲染。
- 生产或正式演示环境必须使用独立密钥、关闭调试模式并启用 HTTPS。

## 3. 本学期新增建设需求

### 3.1 建设范围与成果定义

本学期不重复开发已有聊天功能，而是在既有系统上完成以下五类增量：

1. **客户端产品化**：形成真实可安装的 Windows App 和 Android App。
2. **服务云端化**：部署可从公网访问、支持持久化和安全通信的正式服务。
3. **通信可靠化**：支持跨网络、跨平台、断线重连、消息去重和状态同步。
4. **加密多设备化**：研究并实现适合多客户端的设备与密钥管理策略。
5. **测试工程化**：形成覆盖黑盒、白盒、安全、性能和兼容性的质量体系。

本学期成果必须能够通过安装包、云端地址、跨设备操作、自动化测试输出、覆盖率报告、缺陷记录和部署文档加以证明。仅展示旧页面或重新执行旧测试不能单独构成本学期主要成果。

### 3.5 公网云部署需求

正式云环境推荐采用如下结构：

```text
Windows App / Android App / Browser
                  ↓ HTTPS / WSS
             Nginx 反向代理
                  ↓
         Django ASGI / Daphne
            ↙             ↘
       PostgreSQL         Redis
             ↓
     持久化磁盘或对象存储
```

| 编号 | 需求 | 详细说明 | 优先级 | 验收要点 |
| --- | --- | --- | --- | --- |
| NEW-CLD-001 | 公网域名 | 系统通过稳定的公网域名访问 | P0 | 校外或不同网络的设备可解析并访问 |
| NEW-CLD-002 | HTTPS/WSS | 页面、API、文件和 WebSocket 全部使用安全连接 | P0 | HTTP 自动跳转 HTTPS；客户端使用 `wss://` |
| NEW-CLD-003 | 反向代理 | 使用 Nginx 或等价组件终止 TLS 并代理 HTTP/WebSocket | P0 | WebSocket 升级、超时和上传大小配置正确 |
| NEW-CLD-004 | 正式 ASGI 服务 | 使用 Daphne 或等价 ASGI 服务运行 Django | P0 | 正式环境不使用 `manage.py runserver` |
| NEW-CLD-005 | PostgreSQL | 正式业务数据迁移至 PostgreSQL | P0 | migrations 可执行，重启/升级后业务数据完整 |
| NEW-CLD-006 | 数据迁移 | 如需保留既有数据，应提供 SQLite 到 PostgreSQL 的迁移方案 | P1 | 迁移数量和关键关系校验一致 |
| NEW-CLD-007 | Redis Channel Layer | 正式 WebSocket 消息分发使用 Redis | P0 | 多进程/多客户端场景消息可正确到达，Redis 不暴露公网 |

### 3.6 真实聊天与可靠性需求

真实聊天验收至少使用两台不同设备和两个不同用户账号，并尽量处于不同网络环境。仅在同一浏览器的不同标签页操作不能作为最终跨端验收证据。

| 编号 | 需求 | 详细说明 | 优先级 | 验收要点 |
| --- | --- | --- | --- | --- |
| NEW-REL-001 | 跨网络聊天 | 不同公网网络中的用户可完成联系人、私聊和群聊 | P0 | Windows 与 Android 完成双向消息演示 |
| NEW-REL-002 | 唯一消息 ID | 客户端为每条待发送消息生成稳定唯一 ID | P0 | 重试期间 ID 不改变，不与其他消息冲突 |
| NEW-REL-003 | 消息幂等 | 服务端识别重复提交并返回已有结果 | P0 | HTTP/WebSocket 重试不会产生重复逻辑消息 |
| NEW-REL-004 | 发送状态机 | 客户端展示发送中、已发送、已送达、已读和失败状态 | P0 | 状态转换有明确触发条件，不倒退为非法状态 |

### 3.7 多设备与密钥演进需求

多设备 E2EE 是本学期具有研究价值的增强方向。为控制工作量，采用分级交付：P0 确保单个可信设备安全工作；P1 支持多设备接收新消息；P2 研究经授权的历史迁移或恢复。

| 编号 | 需求 | 详细说明 | 优先级 | 验收要点 |
| --- | --- | --- | --- | --- |
| NEW-DEV-001 | 设备标识 | 每个客户端实例具有稳定且不可轻易冲突的设备标识 | P1 | 同一账号不同设备可被区分和管理 |
| NEW-DEV-002 | 独立设备密钥 | 每台设备独立生成和保存私钥，服务端只保存公钥 | P1 | 一台设备的私钥不直接复制到其他设备或服务端 |
| NEW-DEV-003 | 设备列表 | 用户可查看与账号关联的有效设备及最近活动时间 | P1 | 只允许本人查看，信息足以识别异常设备 |
| NEW-DEV-004 | 撤销设备 | 用户可撤销不再使用或可疑的设备 | P1 | 被撤销设备不能继续接收新消息和密钥材料 |
| NEW-DEV-005 | 多设备分发 | 发送消息时向接收者的有效设备分别准备可解密数据 | P1 | 每个有效设备能解密新消息，撤销设备不能解密后续消息 |
| NEW-DEV-006 | 新设备限制 | 新设备不得未经授权自动解密全部历史消息 | P0 | 历史访问策略有明确提示和测试证据 |
| NEW-DEV-007 | 密钥变化提示 | 联系人新增设备或密钥变化时提示重新验证 | P1 | 新密钥不自动继承旧密钥的可信状态 |
| NEW-DEV-008 | 安全存储适配 | Windows 与 Android 分别使用适合平台的敏感信息保护机制 | P0 | 普通文件、日志和 Web Storage 中无可直接读取私钥 |
| NEW-DEV-009 | 历史迁移 | 经用户明确授权后，可采用安全方案迁移历史解密能力 | P2 | 授权、加密、撤销和失败恢复过程有设计与测试 |

#### 3.8.2 黑盒测试方法要求

黑盒测试至少包含：

- 等价类划分：账号、表单、搜索、文件和消息输入；
- 边界值分析：字段长度、文件大小、分块索引、分页、消息密文大小；
- 判定表：联系人、拉黑、成员角色和消息权限组合；
- 状态迁移：好友申请、群邀请、消息、文件和连接状态；
- 因果图：多条件权限判断及结果组合；
- 场景法：注册—加好友—跨端聊天—断网—恢复—补取；
- 错误推测：重复点击、重复提交、后台恢复、服务重启和磁盘不足；
- 探索性测试：跨平台交互、弱网和异常生命周期。

#### 3.8.3 白盒测试方法要求

白盒测试至少包含：

- 语句覆盖和分支覆盖；
- 复合条件的真/假组合；
- 关键业务基本路径；
- 分页、分块和重试循环的零次、一次、典型及上限路径；
- 异常捕获、事务回滚和资源清理路径；
- 权限校验前后的数据流和副作用检查；
- 未覆盖代码的原因与风险说明。

#### 3.8.4 安全测试范围

安全测试以 OWASP Top 10 和即时通信业务风险为参考，至少覆盖：

- SQL 注入、XSS、CSRF 和开放重定向；
- 身份认证绕过、账号枚举和会话固定；
- 水平越权、垂直越权和群角色越权；
- 文件类型欺骗、超大文件、路径穿越和未授权下载；
- AI 服务地址 SSRF；
- Cookie、HTTPS、CSP 和安全响应头；
- 日志、安装包、浏览器存储及移动端存储中的敏感信息；
- 服务端数据库、HTTP 和 WebSocket 中的 E2EE 明文泄露；
- Python、Node.js 和 Android 第三方依赖漏洞。

#### 3.8.5 性能与稳定性基线

以下指标作为首版验收目标，执行前可根据云服务器配置形成经小组评审的调整记录：

| 指标编号 | 场景 | 首版目标 |
| --- | --- | --- |
| PERF-001 | WebSocket 并发连接 | 100 个并发连接持续 10 分钟，无服务崩溃 |
| PERF-002 | 消息吞吐 | 每秒 20 条聊天消息持续 10 分钟，无服务端重复记录 |
| PERF-003 | 实时延迟 | 正常网络下 95% 消息在 1 秒内对接收端可见 |
| PERF-004 | HTTP 响应 | 95% 普通 API 请求不高于 500 ms |
| PERF-005 | 重连时间 | 网络恢复后客户端 30 秒内恢复实时连接 |

## 5. 界面需求

### 5.1 总体布局

1. 桌面聊天界面采用侧边栏、聊天区和信息面板组成的分区布局。
2. 联系人、设置、群组等子页面优先在侧边栏区域切换，聊天区保持上下文。
3. 当前会话、未读数、在线状态和操作状态应具有清晰视觉反馈。
4. 页面应支持浅色和深色主题，文字与背景保持基本可读对比度。
5. 主要按钮、输入框、菜单和提示不得被常见窗口尺寸遮挡。

### 5.2 认证页面

- 登录页应提供用户名/邮箱输入框、密码输入框、登录按钮和注册链接。
- 注册页应提供完整注册字段、提交按钮及返回登录入口。
- 字段错误应在页面上以用户可理解的语言显示，不展示异常堆栈。
- 表单应支持键盘操作，密码字段不以明文默认显示。

### 5.3 聊天页面

- 会话列表应展示名称、头像、最后消息摘要、时间、未读及置顶/静音状态。
- 聊天头部应展示目标用户或群组基本信息及相关操作入口。
- 消息区应区分发送和接收消息，并显示发送状态、时间、回复或文件信息。
- 输入区应支持文本输入、发送、文件入口和必要的失败反馈。
- 解密失败、网络中断、权限失败和文件失效必须显示明确状态。

### 5.4 设置页面

- 设置首页应提供个人资料、通知、隐私、安全、数据和存储、通用设置等入口。
- 已实现设置应能读取当前值、修改并保存。
- 尚未形成完整闭环的设置必须显示为占位或未实现，不能伪装为可用。

### 6.2 数据完整性规则

1. 用户名、好友关系、会话成员关系、消息客户端标识等唯一性由数据库约束和业务校验共同保证。
2. 好友申请、群邀请、消息状态和文件状态必须使用定义的有限状态值。
3. 私聊会话必须且只应包含合法的两名有效参与者。
4. 群主在有效群聊中应保持唯一；角色变更不得产生无群主状态。
5. 群消息接收者记录必须关联同一群消息和唯一接收用户。
6. 文件分块索引在单个文件内唯一，完成前必须满足分块数量和摘要要求。
7. 私钥、会话密钥、文件密钥明文和 E2EE 消息明文不得保存到服务端数据库。
8. 用户删除、退出或清理操作不得越权修改其他用户独立数据。

### 6.3 数据保留与清理

- 会话清空和用户侧删除默认只改变当前用户可见性。
- 自动删除设置按用户和会话的有效规则计算。
- 过期或取消的临时上传应由清理命令移除。
- 数据库备份、测试数据库、媒体缓存和运行日志不属于源代码交付物。
- 正式环境中的业务数据删除需遵守课程演示口径和实际部署策略。

## 7. 外部接口需求

### 7.1 HTTP 接口

1. 页面接口返回 HTML，业务接口主要返回 JSON 或文件流。
2. 写操作应限制允许的 HTTP 方法并执行身份、权限和 CSRF 校验。
3. 参数错误使用 400 类响应；未认证、无权限和资源不存在应使用相应语义响应。
4. JSON 错误响应应包含稳定错误码或可理解说明，不返回调试堆栈。
5. 上传下载接口必须执行会话成员和文件持有者权限校验。

### 7.2 WebSocket 接口

1. 连接阶段验证用户会话和请求来源。
2. 消息事件采用结构化 JSON，至少包含事件类型和业务数据。
3. 无效 JSON、未知事件、缺失字段和越权事件应返回可识别错误。
4. 私聊事件仅发送给通信双方；群聊事件仅发送给有效成员。
5. HTTP fallback 与 WebSocket 对同一业务规则应保持一致。

### 7.3 AI 服务接口

1. 外部端点必须使用 HTTPS 并通过主机允许规则。
2. 系统支持 OpenAI 兼容 Chat Completions 及 Anthropic Messages 风格协议。
3. 外部服务失败、超时或返回异常时，系统应提供明确错误或安全回退。
4. 模型请求只包含用户主动输入的助手内容及必要系统提示。

### 7.4 文件系统接口

1. 媒体、头像和加密文件只能写入配置允许的目录。
2. 文件名、上传 ID 和存储路径不得允许目录穿越。
3. 服务端存储的是加密文件内容，不应保存客户端文件密钥明文。

| NFR-SEC-004 | 正式环境启用 HTTPS、HSTS、安全 Cookie 和内容类型保护 | `DEBUG=False` 时相关安全配置生效 |
| NFR-SEC-005 | 正式环境必须显式设置密钥 | 未配置 `DJANGO_SECRET_KEY` 时拒绝以正式模式启动 |
| NFR-SEC-006 | 登录错误避免账号枚举，跳转避免开放重定向 | 对应异常输入测试通过 |
| NFR-SEC-007 | AI 外部端点受 SSRF 防护约束 | 不安全 URL 和未允许主机被拒绝 |
| NFR-SEC-008 | 文件上传执行大小、摘要、分块和权限校验 | 非法文件请求不落为有效文件 |

### 8.2 可靠性与一致性

| 编号 | 需求 | 验收指标 |
| --- | --- | --- |
| NFR-REL-001 | 好友接受、建群和关键状态变更使用事务保证一致性 | 中途失败不产生半完成关系 |
| NFR-REL-002 | 私聊和群聊消息支持客户端 ID 幂等 | 重复提交不产生重复逻辑消息 |
| NFR-REL-003 | WebSocket 失败时提供 HTTP 备用发送 | 备用路径遵守同一权限和数据规则 |
| NFR-REL-004 | 单条消息解密失败不影响其他消息和页面 | 错误被局部展示，页面仍可操作 |
| NFR-REL-005 | 外部 AI 服务故障不影响核心通信功能 | 助手失败时私聊和群聊仍可使用 |

### 8.3 性能

| 编号 | 需求 | 建议验收指标 |
| --- | --- | --- |
| NFR-PER-001 | 常规页面和本地接口具备可接受响应时间 | 课程环境下 95% 普通 HTTP 请求不高于 2 秒 |
| NFR-PER-002 | 在线消息具有可接受延迟 | 本机或局域测试中消息可见延迟通常不高于 1 秒 |
| NFR-PER-003 | 历史消息和搜索使用分页或结果限制 | 大量数据时单次响应不返回无限记录 |
| NFR-PER-004 | 文件采用分块传输 | 单块失败可重试，无需重新上传全部文件 |

> 性能阈值需在后续测试计划中结合课程设备、网络和数据规模最终确认。

### 8.4 易用性与可访问性

1. 核心流程的主要操作入口应清晰可见，错误信息应可理解。
2. 相同操作在不同页面应使用一致术语、图标和反馈方式。
3. 页面应支持常见桌面窗口尺寸，重要操作不因缩放被遮挡。
4. 表单应具备标签、焦点和键盘提交能力。
5. 深浅主题下文字、按钮和状态应具有足够可辨识度。

### 8.5 兼容性

1. 核心 Web 功能至少支持课程指定的当前 Chromium 浏览器。
2. 使用 Web Crypto API 的浏览器必须提供安全上下文及所需算法。
3. Electron 使用的 Chromium 内核应与 Web 页面主要功能兼容。
4. Windows 为主要课程实验环境；自动化测试应能在 GitHub Actions 的 Linux 环境运行。

### 8.6 可维护性与可测试性

1. 账号功能归入 `accounts`，聊天相关功能归入 `chat`，项目配置归入 `ichat_pro`。
2. 数据结构变化通过 Django migrations 管理，不直接修改已交付数据库结构。
3. 每项核心需求应有唯一编号，并可关联任务、用例、缺陷和提交。
4. 核心后端功能使用 Django TestCase/TransactionTestCase 测试；前端加密逻辑使用 Node.js 测试。
5. 合并前至少执行 Django 配置检查、迁移检查和核心自动化测试。
6. 测试数据、密钥、数据库和本地依赖不得提交为正式源码。

## 9. 核心业务规则

### 9.1 账号规则

1. 用户名必须唯一，邮箱登录仅匹配已存在的绑定邮箱。
2. 账号被禁用后不能建立新的登录会话。
3. 用户只能修改自己的资料、设置和会话状态。

### 9.2 联系人规则

1. 用户不能将自己添加为联系人。
2. 双方已是联系人时不能再创建有效好友申请。
3. 同一对用户不能同时存在多个等价的待处理申请。
4. 只有接收者可以接受或拒绝申请，只有发起者可以取消申请。
5. 一条 Contact 关系在当前业务语义中代表双方互为联系人。

### 9.3 私聊规则

1. 创建新私聊必须通过联系人、隐私、账号状态和拉黑规则。
2. 已存在有效私聊时必须复用，不能创建重复会话。
3. 只有有效会话成员可读取历史、发送消息或修改消息状态。
4. 删除联系人不应自动删除已经存在且仍有效的历史会话。

### 9.4 群聊规则

1. 创建者自动成为群主，一个有效群聊只能有一名群主。
2. 普通成员邀请需要管理员审核；群主和管理员按权限直接邀请。
3. 新成员只能获得加入后为其生成的群消息密文。
4. 退出或被移除成员不能接收新的群消息和密钥。
5. 群成员变化必须更新成员版本，以防使用过期成员列表分发密文。

### 9.5 消息与加密规则

1. 服务端不接受客户端将聊天明文作为持久化字段提交。
2. 加密载荷必须包含协议要求的密文、随机数、认证信息、算法和密钥版本。
3. 发送者副本与接收者副本分别保存，满足双方历史解密需要。
4. 消息客户端 ID 用于识别网络重试，不能作为越权覆盖其他消息的手段。
5. 撤回、删除、转发、已读等操作必须验证操作者与消息关系。

### 9.6 文件规则

1. 文件在客户端加密后上传，服务端只保存密文分块。
2. 每个有权解密文件的用户拥有独立的加密文件密钥记录。
3. 文件转发到新会话时必须为新目标重新准备合法密钥记录。
4. 文件未完成、已取消、已删除或已过期时不得作为正常文件发送或下载。

### 9.7 AI Assistant 规则

1. AI Assistant 是独立辅助面板，不是联系人、Bot 用户或会话成员。
2. AI Assistant 不自动读取现有私聊、群聊、私钥、会话密钥或文件密钥。
3. 用户必须主动输入或粘贴内容后才能向模型服务发送。
4. 模型配置按用户和助手隔离，不得使用其他用户配置。

## 10. 当前范围外与后续规划

以下能力不是当前版本的完整交付需求，不得按“已实现功能”验收：

1. 语音通话和视频通话。
2. 移动端原生 App。
3. 完整的 Signal Protocol、Double Ratchet 或 Sender Key 协议。
4. 真正的 P2P 网络通信。
5. 完整多设备密钥同步与冲突处理。
6. Channel、完整 Bot、Agent Gateway、RAG 知识库和长期记忆。
7. WebAuthn Passkey、完整密码锁和完整两步验证闭环。
8. 完整云端贴纸、生日提醒和全局快捷键同步。
9. 面向大规模公网部署的高并发、容灾及内容审核体系。
