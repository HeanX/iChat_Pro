## 1. 问题定义

### 1.1 "历史密钥迁移"迁移的是什么

服务端与客户端各自保存的密钥材料：

| 材料 | 存放位置 | 生命周期 | 迁移需求来源 |
| --- | --- | --- | --- |
| **身份私钥（当前版本）** | 客户端 IndexedDB（`key-manager.js:108-117`，键 `privateKeyStoreKey(userId)`） | 随浏览器/设备存续；非提取式 CryptoKey（桌面 safeStorage 场景不可导出） | 换设备/重装后，旧密文的**解密能力**跟着私钥走 |
| **历史版本私钥** | 同上，键带 `keyVersion`（`savePrivateKey(userId, key, version)`，`key-manager.js:112-114`） | 仅当版本化保存时存在；**没有版本化保存的旧私钥不可恢复** | 解密轮换前的历史密文 |
| **服务端公钥多版本历史** | `UserPublicKey`（`is_active=False` 的历史行永久保留） | 永久 | 只需读取，无需迁移 |
| **`KeyTrust` 信任记录** | 服务端，按指纹 | 永久（#189 确立"旧记录保留审计"） | 迁移后对新指纹的信任需**用户显式重授** |
| **客户端信任缓存** | localStorage `ichat_peer_identity:<userId>`（按版本记指纹） | 随浏览器 | 换设备即丢——迁移**不应**复制它（见方案 A 的撤销分析） |

> 补充（完整性论证）：群聊 `sender_copy` 与文件密钥都由**按 `key_version` 的身份私钥**保护
> （`group-chat-e2ee.js:409-441`、`private-chat-e2ee.js:358-368`，读取经 `getCurrentPrivateKey(keyVersion)`，
> `key-manager.js:77-79`），因此恢复对应版本的私钥后它们**自动恢复可解**，不是独立的迁移对象；
> 上表的迁移对象清单因此是完备的。

**核心矛盾**：解密历史密文的能力绑定在**设备本地**的私钥上，而服务端按契约**永远不持有私钥**（上传接口显式拒绝 `private_key` 字段，`accounts/views.py:1039-1041`）。因此"迁移"只能走**端到端**路径——要么用户手动搬备份，要么由旧设备把解密能力**安全地**授予新设备。服务端最多做公钥/元数据的搬运，绝不能成为私钥的传递方。

### 1.2 现有能力盘点（不新造轮子）

| 已有能力 | 位置 | 与本研究的距离 |
| --- | --- | --- |
| JSON 备份导出/导入（`format_version: 1`，JWK 私钥 + 指纹校验 + 归属校验） | `key-manager.js:316-332`（导出）、`:334-370`（导入，两重校验：L337-347 结构与归属、L358-365 x/y/SPKI/指纹一致） | 已是**单文件人工迁移**的完整实现，且**UI 入口已存在**（`settings_panel.html:367-395` 与 `chat.html:340-365` 的导出/导入按钮）——"方案 A"不是从零建入口，而是补警示与操作文档（见方案 A 表） |
| 桌面 safeStorage 场景的"创建后待备份"暂存（`enc:` 前缀，sessionStorage） | `key-manager.js:26-43` | 弥补桌面端密钥不可导出的限制；导出动作内即清除暂存（`exportBackup` L331），**有且仅有一次**导出机会，这是 UX 风险点 |
| 版本化私钥存储 | `key-manager.js:108-117` | 迁移多版本私钥的载体已存在；`savePrivateKey` 的全部调用点只写"当前版本"（generate/import/legacy-migration/upload 盖章），**没有任何流程会保存"历史版本"私钥**——未版本化保存过的旧私钥不可恢复 |
| 联系人指纹展示与重验（#189 确立的"新指纹默认未信任"语义） | `accounts/views.py` 的 `contact_fingerprints_view`（L1151 起，按指纹回显各版本 `trust_status`）与 `key_trust_list_view`（L1247 起，`key_changed` 于 L1257-1260 内联计算） | 迁移后对端如何感知"你换了设备"——复用既有提醒机制，不需要新协议 |

## 2. 威胁模型约束

对齐对象是**本仓库既有契约**，而非某份独立威胁模型文档（基线 `cfe53be` 上不存在 ADR-P4-04；
E2EE 威胁模型由 T38 在另一分支交付，尚未合入）。逐条锚定：

- **T-α 私钥永不出端**：锚定 `docs/phase4/requirements.md` §3.5 共同安全约束 1（服务端不存用户私钥）；
  代码证据：上传接口显式拒绝 `private_key`/`session_key`/`file_key`（`accounts/views.py:1039-1041`）；
- **T-β 授权必须是人给出的**：锚定 requirements.md §3.5 与追溯矩阵 NEW-DEV-009（"仅经用户授权"）——自动授予等于把"持有旧设备"升级为"持有账号所有历史"；
- **T-γ 失败必须可恢复**：迁移中断（关页、断网、导入坏文件）不得造成两边都不可用；
- **T-δ 撤销必须可追溯**：迁移完成后旧设备的授权必须能被显式收回（衔接 #168 的 `revoked_at`）；
- **T-ε 不扩大信任**：迁移**不得**让新设备继承任何信任判定——即 #189 的验收原句
  "新密钥不自动继承旧信任状态"（requirements.md §3.5 约束 4：新公钥/设备不自动继承旧指纹的已验证状态）。

> 五条约束无一是本研究自造；T-α/T-ε 在 requirements.md §3.5 白纸黑字，T-β 是 #170 验收原句。
> 方案 C 的拒绝（§3）依据的正是 T-α 的契约条文，而非主观偏好。

## 3. 方案评估

### 方案 A：人工备份文件迁移（现状能力的产品化）

**流程**：旧设备导出 JSON 备份 → 用户通过**带外渠道**（U 盘/局域网直传，明确不建议聊天软件本身——理由见 §4.1 第 7 行）传到新设备 → 新设备导入 → 服务端公钥与指纹校验通过（现有校验）→ 完成后**在旧设备上主动登出并清除本地密钥**（T-δ）。

| 维度 | 评估 |
| --- | --- |
| 授权（T-β） | 天然满足：备份文件在用户手里，导入这个动作即授权 |
| 失败路径（T-γ） | 导入失败时新设备什么都没写（现有实现先两重校验后落库：`key-manager.js:337-347` 结构与归属、`:358-365` 密钥一致性）；旧设备的密钥未动 → 可重试 |
| 撤销（T-δ） | **弱**：依赖用户自觉清旧设备；若不清，旧设备仍是全权身份（阶段 1 无设备模型，无法远程吊销） |
| 多版本历史 | **不支持**：现有备份只含当前版本（`backupRecord = pendingBackup || record`，L323，单记录）；历史版本私钥若没版本化保存过，迁移后**依然解不开旧密文** |
| 实现成本 | **近似零代码**——导出/导入的 UI 入口**已存在**（`settings_panel.html:367-395`、`chat.html:340-365`）。真实增量只有两件：导出警示文案（Q-A）与一份迁移操作文档。本卡不实施它们（见 §5），但不再需要"新建入口" |

**结论：作为 v1 推荐**。它是唯一不依赖 #167–#169 就能落地的方案，且复用已通过评审的代码与既有 UI。

### 方案 B：旧设备在线授权新设备（"密钥交接协议"）

**流程草图**：新设备生成临时密钥对 → 用户在**旧设备**上看到新设备的指纹并确认 → 旧设备用临时公钥加密"当前私钥 + 历史版本私钥包" → 服务端**仅作中转信箱**（加密 blob，无法解密）→ 新设备取走解密。

| 维度 | 评估 |
| --- | --- |
| 授权（T-β） | 满足：确认动作在持有私钥的旧设备上完成，可加"输入账号密码"二次确认 |
| 撤销（T-δ） | 强：交接完成即等价于"旧设备主动移交"，可在移交时刻置旧设备 `revoked_at`（依赖 #167 落地） |
| 多版本历史 | 支持方案明确（把版本化私钥打包进交接载荷） |
| 实现成本 | **高**：新协议事件（服务端信箱）、旧设备 UI、新设备 UI、中转 blob 的 TTL 与防重放；并且**必须**等 #167 的设备模型落地后才有"设备"主语 |
| 新增风险 | 中转信箱成为新的攻击面：若 blob 未取走即过期，用户以为迁移完成实则未完成（T-γ 的变体）；需要"迁移状态可查询"的接口 |

**结论：作为 v2 方向**，前置依赖 #167 落地，且其"设备作为加密目标"的抽象必须与 ADR-P4-05 §6 的
待决问题（Q1–Q5：双持钥、`recipients` 语义、撤销广播、僵尸归档、数据保留）的会签结论一致——
那五个问题在 #167 的 ADR 里定义，不在本报告里。**不建议在本学期实现**，但草图已足够指导 #169 的 recipients 设计。

### 方案 C：服务端托管加密备份（私钥加密后存服务端）

**被明确拒绝**。理由：
1. 备份口令的强度完全取决于用户，而服务端无法验证；口令弱 = 全部历史密文沦陷；
2. 服务端持有"可用口令暴力的密文"**直接违反成文契约**——`docs/phase4/requirements.md` §3.5
   共同安全约束 1"服务端不存用户私钥"（现行威胁模型的资产边界同样成文于
   `docs/iChat Pro 浏览器端安全威胁模型.md`），需要重新过威胁评审才能例外化；
3. 与现有实现取向冲突：代码刻意让"能不落明文就不落"——桌面端 pending backup 必须 `enc:`
   safeStorage 密文、web 明文回退要大声警告（`key-manager.js:26-43`），而这是**客户端自己加密自己存**；
   方案 C 变成"服务端替用户存可暴力的密文"，性质不同。**用户的信任模型是"服务器拿不到密钥"，
   而非"服务器拿到的都是密文"**——这条是第 1、2 条的推论，不是独立论据。

## 4. 推荐路径与验收映射

**推荐**：v1 采用方案 A（零代码，产品化现有备份能力），v2 立项方案 B（依赖 #167）。

### 4.1 方案 A 的失败与撤销路径（对应验收"失败和撤销路径明确"）

| 场景 | 行为 | 用户看到 |
| --- | --- | --- |
| 导入文件损坏/篡改 | 现有校验拒绝（L337-347 结构、L358-365 密钥一致性），**不落库**；新设备保持无密钥状态 | 明确报错"备份无效或属于其他账号"，可重新导出再试 |
| 导入了**别人账号**的备份 | `record.user_id !== String(userId)` 拒绝（L339） | "备份属于其他账号" |
| 导入成功但**中途断网** | 无影响——导入是纯本地操作，公钥上传是唯一网络步骤且可重试 | 上传失败提示重试，本地私钥已安全保存 |
| **备份文件经不当渠道外泄**（用户自己把 JSON 发进聊天软件/邮箱） | 服务端**不可感知、不可撤销**：该文件即全部历史密文的解密能力，持有人可解密该账号此前收到的所有私聊/群消息副本 | 无任何系统提示——只能靠导出时的警示文案（Q-A）与用户文档事前预防；这是方案 A 最大的固有风险 |
| **备份是未来格式**（如 `format_version: 2`） | v1 客户端直接拒绝（L338 `format_version !== 1`）——方向安全（宁可拒也不导入半认识的密钥），但用户会困惑"明明是新备份却导入失败" | "备份无效"；文档需写明"新版本客户端导出的备份，旧客户端读不了" |
| 旧设备未清除 | 阶段 1 无法远程吊销（无设备模型）；**文档必须写明**"迁移后旧设备仍有解密能力，请手动登出并清除" | 设置页文案 + 迁移完成后的显式提示 |
| 迁移后联系人信任 | 对端看到 `key_changed=true`（若迁移含轮换）或不变（同指纹）；**不自动继承**任何信任（T-ε） | 对端按既有提醒流程重验 |
| 迁移前已丢失旧设备 | 唯一恢复路径 = 用户在**更早时候**导出过备份；没备份则历史密文永久不可解——这是设计决定，不是缺陷，但必须写进用户文档 | — |

## 6. 待决问题

- **Q-A**：方案 A 上线时，是否在备份导出时**明文警示**"此文件含私钥，泄露 = 全部历史沦陷"？（倾向：是，导出弹窗加一行红字）
- **Q-B**：是否支持导出**多版本**备份（把 IndexedDB 里版本化的私钥打包）？现有 `format_version: 1` 是单记录格式，扩展需 `format_version: 2` 与兼容读取——涉及对既有备份文件的向后兼容承诺，建议放 v2 与方案 B 一起做。
- **Q-C**：迁移完成的判定由谁写下来？（阶段 1 无服务端设备记录 → 只能是客户端本地的"迁移完成标记"；这算不算需要服务端见证的状态？倾向：不算，避免服务端持有可推断的元数据。）
