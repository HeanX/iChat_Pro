# Phase4 Agent 工作包与交接模板

> 本文用于用户把任务发给其他Agent，不代表已经创建、派发或执行这些任务。  
> 任务号保留原 `P4 Txx` / `P4 Test Txx`，下方WP是本次整理的协作工作包，不替换原编号。

## 1. 通用工作约定

1. 先读本目录README、requirements、technical-design，再读所领任务在tasks.md中的原验收行。
2. 先核对现有实现和工作区改动，不删除、覆盖或提交其他人的资料。文档之外可能还有用户改动。
3. 只实现所领工作包，优先P0；对已有可用能力做增量增强，不重写账号/聊天框架。
4. 公开约定的新增接口、模块与模型先交小型设计/ADR，再实施；可自主解决常规实现选择，只有缺少真实服务器、域名、签名材料等资源时才提出具体所需信息。
5. 保持Django Session/CSRF和既有E2EE兼容。不能通过关闭来源验证、明文存钥、公开整个media、把服务密钥打入安装包来打通流程。
6. 跑有意义的模块测试与本目录基线检查；真实平台/云测试缺资源时报告未验证，不能填“通过”。
7. 交付代码、迁移、接口说明、实际证据、未完成项和后续依赖，避免只回一段方案。

分支优先沿用课程规范 `feature/p4-txx-short-name` / `test/p4-test-txx-short-name` 等；执行环境若强制其他前缀，保留任务号并记录。不要在用户未要求时自动发布生产、变更GitHub任务负责人或合并他人分支。

## 3. 实施顺序与依赖

### 第一轮：建立可验证骨架

- WP00复核需求与347条测试基线，登记当前缺陷。
- WP01先完成配置、依赖、部署模板与本地正式依赖环境；真实域名/服务器具备后再完成公网证据。
- WP02先固化T31协议、错误码、服务层接口与补取契约，开始T32/T33/T36后端/共享模块开发。
- WP03先完成可配置云Origin与构建骨架；WP04先完成T22登录/WS/安全存储技术验证。
- WP05先定义KeyStore能力、旧钥迁移限制、测试向量与原生桥边界。
- WP06同步设计负向测试；WP07先接入已有检查和Node测试。

原任务T31依赖T14/T24。设计和后端测试可提前推进，最终T31验收仍等待双端安装并完成协议互通，不能为了并行工作直接删掉原依赖。

### 第二轮：P0集成

云HTTPS/WSS与真实PG/Redis就绪→Windows云模式exe / Android APK→可靠发送、ACK/重试、补取与生命周期→平台安全存储→双账号跨设备公网私聊→弱网、明文边界、备份恢复和CI核心门禁。

T20/T26各自保留平台验收责任，连接/重试算法归WP02共享实现；平台Agent负责触发网络/生命周期事件，不各维护一套状态机。

### 第三轮：P1与P2

P0证据成立后，推进群聊文件跨端、系统集成、多设备身份/撤销/新消息分发、完整UI自动化/性能稳定性、监控和发布流程。自动更新、完全退出云推送和历史迁移最后评估。

## 4. 公共文件协调规则

| 公共位置 | 集成责任 | 其他工作包方式 |
| --- | --- | --- |
| chat.js与新共享连接/同步模块 | WP02 | WP03/WP04/WP05提供接口与小范围调用改动，不同时整文件重构 |
| accounts/models.py、chat/models.py、迁移 | 指定单一迁移负责人（建议WP02整合） | WP05提交模型设计；确认后串行生成编号/合并 |
| chat/views.py、chat/urls.py、accounts/urls.py | WP02整合消息路由；账号路由与WP05协调 | WP01健康接口只添加独立小模块及最小路由改动 |
| requirements.txt、settings.py | WP01 | WP02/WP05/WP07提出依赖/配置需求，由WP01统一合并 |
| 根package.json/lock | 指定一个依赖整合人 | desktop/mobile尽量使用自身构建目录，根只做共享脚本 |
| 模板公共脚本区和CSS | WP04负责移动布局，WP02负责加载顺序 | 平台桥和KeyStore脚本由对应包交接口后顺序集成 |
| .github/workflows | WP07 | WP06交命令、结果格式和阈值，客户端交构建命令 |
| 需求与验收证据 | WP00/WP08 | 开发包提交实际结果，由文档包统一索引 |

不同Agent可以分支并行准备改动，但共享文件的最终合并必须串行。没有契约的前置依赖时，先实现与之无关的骨架/测试，别用假接口完成产品验收。

## 6. 各包补充提示词

以下文字可接在总提示词后；一次只选相应工作包。

### WP01 云端

```text
实现P4 T04–T13的配置与部署交付。先补齐PostgreSQL驱动/channels-redis、
生产配置强校验、受信反向代理/CSRF、静态收集和鉴权媒体方案。新增deploy模板、
健康接口、备份/独立恢复/回滚手册与测试。现有代码读取DJANGO_DEBUG，不是DEBUG。
不将整个media公开，不把秘密写进镜像/安装包；真实公网操作需使用用户提供的资源。
与WP02协调路由，集中整合requirements/settings；注明哪些仅本地验证。
```

### WP02 可靠消息

```text
实现P4 T31–T37。先抽取HTTP/WS共用消息服务，修正幂等校验顺序、请求冲突、
created/replayed副作用和按查看者密文投影。设计稳定同步序号/持久事件与补取API，
覆盖文件、转发等全部写入路径，处理ACK丢失、迟到确认、分页并发和漏推送。
接入共享连接/待发箱/状态机；与双端和KeyStore包保持接口一致。
使用PostgreSQL验证并发事务，不能只依赖SQLite测试宣布可靠性完成。
```

### WP03 Windows

```text
实现P4 T14–T21。云模式使用完整HTTPS Origin且不启动本地Python；保留显式开发模式。
生成有版本和校验值的Windows安装包，排除数据库、media、.env和开发依赖。
先完成安装/卸载、离线反馈、共享连接模块和安全存储；P1再接托盘/通知/文件。
遵守WP05 KeyStore契约，所有IPC验证受信frame、Origin和参数；不暴露通用文件读写。
不能把构建成功当成干净Windows安装成功，分别提交证据。
```

### WP04 Android

```text
实现P4 T22–T30。先完成Django模板、Session/CSRF、WSS、WebCrypto/KeyStore兼容原型并写ADR。
可选等价原生WebView混合外壳；若选本地Capacitor前端，要解决JSON初始化与跨Origin认证。
Capacitor server.url热重载配置不能直接当正式方案。固定工具链并生成APK。
实现移动布局、触摸、返回键、生命周期、网络切换、安全存储与权限拒绝路径。
连接算法复用WP02；前台提醒属于P0，后台系统通知P1，完全退出云推送P2。
提交两个API Level或设备配置的实际执行记录，未测试项明确列出。
```

### WP05 E2EE

```text
实现P4 T38–T43，先P0平台存储和威胁模型，再P1设备模型与撤销/分发，历史迁移P2。
复用实际P-256/HKDF/AES-GCM、临时公钥和sender_copy协议，生成跨端测试向量。
清理sessionStorage明文pending backup，定义KeyStore和旧不可导出密钥迁移策略，
禁止静默换钥或删除旧钥。Windows用系统保护，Android按Keystore实际能力验证。
设备身份绑定Session，撤销验证现有WS/HTTP与后续副本分发；新设备不能自动读取旧历史。
模型/迁移与WP02串行整合，保留legacy密文与历史公钥读取。
```

### WP06 测试

```text
负责P4 Test T03–T22；与WP00保留需求追踪，先固化覆盖率范围和高风险逻辑清单。
补HTTP/WS幂等、权限、同步、群历史及加密向量负向测试，再验证真实PG/Redis和双端。
建立黑盒/白盒、安全、弱网、兼容、安装、恢复、性能与稳定性证据；覆盖率分别统计
语句85%/分支75%，高风险目标90%。缺陷记录复现、提交和复测结果。
没有设备或云资源的测试标为未执行，不能以编写脚本替代实测结果；向WP07提供门禁命令。
```

### WP07 CI

```text
实现P4 T44–T50及P4 Test T23。保留现有Django检查，补Node加密、静态/格式、
覆盖率阈值、依赖/秘密扫描、真实PG/Redis服务测试和客户端构建job。
接入隔离测试部署、部署后健康/登录/核心接口冒烟以及可审计发布与回退流程。
P0失败必须使流水线失败，报告和安装包记录版本/commit/checksum；禁止上传密钥。
构建命令依赖客户端包先落地，不能在CI中编造存在的脚本。
```
