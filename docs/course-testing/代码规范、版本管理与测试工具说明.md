## 2. 代码规范

### 2.1 通用要求

1. 文件统一使用 UTF-8 编码，文本文件以换行符结尾。
2. 命名应表达业务含义，禁止使用无意义的拼音、单字母或临时名称。
3. 不得在源码中提交密码、Token、私钥、生产域名密钥或真实用户隐私数据。
4. 新增逻辑应保持职责单一；重复逻辑应提取为函数、类或公共组件。
5. 注释重点说明设计原因、边界和安全约束，不重复描述代码表面行为。
6. 调试输出不得进入正式分支；日志中不得记录密码、会话令牌、私钥和消息明文。
7. 每项改动必须包含与风险相匹配的测试，并能追溯到对应 Issue。

### 2.2 Python 与 Django

- 遵循 PEP 8：变量和函数使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`。
- 导入按标准库、第三方库、项目内部模块分组，禁止无必要的通配符导入。
- View、Consumer、Service 和 Model 分工清晰，复杂业务逻辑不得全部堆积在视图层。
- 修改数据模型时必须提交 Django migration，并执行迁移一致性检查。
- 涉及多表写入、消息状态变更和关键安全操作时，应根据需要使用数据库事务。
- 所有对象级操作必须检查当前用户权限，不能仅依赖前端隐藏按钮。
- 新增复杂公共函数应提供简短文档字符串；适合的参数和返回值应补充类型标注。
- ORM 查询应避免明显的 N+1 问题，批量场景优先使用 `select_related`、`prefetch_related` 等机制。
- 异常处理应保留可诊断信息，同时向客户端返回稳定、无敏感信息的错误响应。

### 2.3 JavaScript 与客户端代码

- 默认使用 `const`，确需重新赋值时使用 `let`，不使用 `var`。
- 变量和函数使用 `camelCase`，类或组件使用 `PascalCase`。
- 网络请求、WebSocket、加解密和本地存储操作必须处理成功、失败、超时和重试状态。
- 来自用户或服务端的文本进入 DOM 前必须安全转义，禁止直接拼接不可信 HTML。
- E2EE 模块应保持“密钥生成—密钥存储—加密—传输—解密”的边界，不得将明文或私钥发送至服务端。
- Windows、Android 和 Web 的公共协议字段保持一致；修改消息结构时同步更新兼容性测试。
- 客户端日志默认不得输出消息明文、密钥材料或完整身份凭据。

### 2.4 HTML、模板与样式

- 优先使用语义化 HTML，并为表单、按钮和交互控件提供明确标签。
- 模板只负责展示和轻量条件判断，复杂业务逻辑放在后端或独立脚本中。
- 避免在模板中堆积大段内联 JavaScript 和 CSS。
- 新页面应兼顾桌面和移动端布局，并检查键盘操作、焦点状态和基本可访问性。

### 2.5 安全编码要求

- 生产配置通过环境变量或秘密管理服务注入，开发与生产配置分离。
- 所有敏感接口验证身份、权限、请求方法、输入长度、类型和文件格式。
- 上传文件校验扩展名、MIME、大小和存储路径，文件名不得直接作为服务器路径。
- 正式环境仅允许 HTTPS/WSS，Cookie 按需启用 `Secure`、`HttpOnly` 和 `SameSite`。
- 依赖升级前执行兼容性和安全回归，发现高危漏洞必须建立缺陷 Issue。

## 3. 源代码与协作管理

### 3.1 管理工具

| 工具 | 用途 |
| --- | --- |
| Git | 本地版本控制、分支与提交历史 |
| GitHub Repository | 远程代码托管和权限管理 |
| GitHub Issues | 需求、任务、缺陷与验收跟踪 |
| GitHub Pull Requests | 代码评审、讨论和合并 |
| GitHub Actions | 自动检查、测试和后续发布流水线 |

### 3.2 分支策略

- `main`：可演示、可测试的稳定分支，禁止直接提交未经评审的功能代码。
- `feature/p4-txx-short-name`：开发类任务，例如 `feature/p4-t14-windows-shell`。
- `test/p4-test-txx-short-name`：测试代码或测试环境任务。
- `fix/p4-txx-short-name`：缺陷修复。
- `docs/p4-txx-short-name`：文档和过程资产。
- `release/vx.y.z`：需要集中稳定化时使用的发布分支。

每个分支原则上只解决一个 Issue；若确需关联多个 Issue，应在 PR 中说明原因和边界。

### 3.3 提交规范

提交信息采用“类型 + 简述 + Issue 编号”的形式：

```text
feat: add Windows reconnect indicator (P4 T18)
fix: reject unauthorized group message request (P4 T34)
test: cover offline message replay (P4 Test T08)
docs: update cloud deployment acceptance criteria (P4 T05)
```

常用类型包括：`feat`、`fix`、`test`、`docs`、`refactor`、`chore`、`ci`。提交应保持小而完整，不混入无关格式化、临时文件或个人环境配置。

### 3.4 Issue 工作流

```text
需求或缺陷提出 → 建立/领取 Issue → 明确验收标准 → 开发或测试
→ 提交 PR → 自动检查 → 同伴评审 → 修改与回归 → 合并并关闭 Issue
```

Issue 至少包含：背景、目标、范围、完成条件、依赖、责任人和证据链接。开发任务编号使用 `P4 T01–P4 T54`，测试任务编号使用 `P4 Test T01–P4 Test T24`。

### 3.5 Pull Request 要求

每个 PR 应填写：

- 关联 Issue 和需求编号；
- 改动内容与不在本次改动范围内的事项；
- 风险点及回滚方式；
- 执行过的测试、结果和证据；
- 涉及界面时提供截图或录屏；
- 涉及协议、数据库或配置时说明兼容性和部署步骤。

合并前至少满足：自动检查通过、无未解决的阻断意见、验收标准有证据、无敏感文件进入版本库。关键安全或 E2EE 改动应由非作者成员复核。

### 3.6 代码评审清单

- 是否只实现了 Issue 约定的范围；
- 是否正确处理权限、异常、空值、重复请求和并发；
- 是否破坏旧客户端、旧数据或既有聊天功能；
- 是否新增或更新了必要测试；
- 是否存在明文密钥、隐私日志、注入、越权或不安全文件访问；
- 测试证据是否可复现，文档和配置是否同步更新。

## 4. 测试工具与质量门禁

### 4.1 工具清单

| 测试层级 | 工具 | 当前状态 | 主要用途 |
| --- | --- | --- | --- |
| 后端单元/集成测试 | Django TestCase、TransactionTestCase | 已使用 | Model、View、权限、数据库和事务测试 |
| E2EE JavaScript 测试 | Node.js | 已使用 | 加密协议与前端加解密逻辑回归 |
| 持续集成 | GitHub Actions | 已使用 | 安装依赖、Django 检查、迁移检查、自动测试 |
| 覆盖率 | coverage.py | 计划接入 | 统计语句、分支覆盖率并识别薄弱模块 |
| Python 静态检查 | Ruff | 计划接入 | 格式、常见错误和代码质量检查 |
| Web 端到端测试 | Playwright | 计划接入 | 浏览器真实业务流程和跨浏览器回归 |
| Android/Windows UI 自动化 | Appium | 计划接入 | 安装包、触控/窗口、权限和跨端流程测试 |
| 接口测试 | pytest/Django Client、Postman/Newman | 计划完善 | API 正常、异常、边界和鉴权测试 |
| 性能测试 | Locust 或 k6 | 计划接入 | 登录、消息发送、WebSocket 并发和稳定性 |
| 动态安全测试 | OWASP ZAP | 计划接入 | 常见 Web 安全风险扫描 |
| 依赖/代码安全 | Bandit、pip-audit、npm audit | 计划接入 | Python 安全规则和第三方依赖漏洞检查 |
| 集成环境 | PostgreSQL、Redis | 计划接入 CI | 正式数据库和 Channel Layer 的真实集成测试 |

“已使用”表示仓库已有对应代码或流水线；“计划接入”表示本学期验收目标，不作为当前完成成果申报。

### 4.2 当前基础检查

```powershell
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test
```

JavaScript E2EE 测试按仓库现有脚本执行。后续统一写入项目脚本和 CI，避免依赖个人机器的全局环境。

### 4.3 目标流水线

1. 安装锁定版本的 Python 和前端依赖；
2. 执行格式、静态分析和秘密扫描；
3. 执行 Django 系统检查与迁移一致性检查；
4. 执行单元、集成、E2EE 和覆盖率测试；
5. 启动 PostgreSQL、Redis 服务完成关键集成测试；
6. 构建 Windows 安装包和 Android APK；
7. 在测试环境执行冒烟、端到端和安全扫描；
8. 保存测试报告、覆盖率、构建物和发布记录。

### 4.4 测试证据要求

每次测试至少记录：版本或提交 SHA、测试环境、用例范围、执行人、开始与结束时间、通过/失败/阻塞数量、失败日志、截图或报告链接，以及对应 Issue。测试数据应为构造数据，不应公开真实聊天内容和密钥。

## 5. 完成定义（Definition of Done）

一个任务只有同时满足以下条件才可标记完成：

- 验收标准全部满足且范围无遗漏；
- 代码、配置、迁移和文档已经提交；
- 相关自动化测试通过，必要的人工测试有证据；
- 同伴评审意见已处理；
- 不存在未说明的高危安全问题或严重回归；
- PR 已关联 Issue，并能从需求追溯到代码、测试和结果；
- 若影响部署，已提供升级、回滚和兼容性说明。

## 6. 禁止事项

- 禁止直接向稳定分支提交未经测试的功能；
- 禁止通过删除或跳过失败测试来“修复”流水线；
- 禁止伪造测试记录、覆盖率、AI 输出或验收截图；
- 禁止提交 `.env`、数据库备份、真实 Token、私钥和个人调试文件；
- 禁止仅凭 AI 生成结果合并代码，所有结果必须经过人工审查和可复现验证。
