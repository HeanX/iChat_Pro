## 三、项目重新定位

上学期 iChat Pro 已经实现账号、联系人、私聊、群聊、WebSocket、端到端加密、文件传输、消息管理、设置中心和 AI Assistant 等基础功能。如果本学期只重新展示这些功能，无法体现新课程的实践增量。

因此，本学期项目定位调整为：

> 将已有 Web 聊天系统升级为可在 Windows 和 Android 真实安装、通过公网云服务跨设备通信，并具备完整软件测试与质量保障体系的产品原型。

本学期主要成果分为五条主线：

```text
已有聊天功能基线

    ├─ Android App 产品化
    ├─ 公网云部署
    ├─ E2EE 与可靠通信增强
    └─ 产业级测试与 CI/CD
```

已有功能作为被测系统和回归基线，不重复作为主要创新成果计入任务完成度。

## 五、需求亮点

### 5.1 亮点一：Windows、Android 与 Web 三端真实可用

项目不再局限于浏览器中的课程演示，而是交付可安装的 Windows 和 Android 客户端。三个客户端连接同一云服务，共享账号、联系人、会话、群组和消息状态。

亮点价值：

- 体现从 Web 原型到真实软件产品的工程升级；
- 研究桌面与移动平台在通知、文件、权限、生命周期方面的差异；
- 形成安装、卸载、兼容性和跨端测试场景。

核心验收：

- 在干净 Windows 环境安装 `.exe`；
- 在 Android 真机或独立模拟器安装 APK；
- 两端通过公网进行双向聊天；
- 消息内容、顺序、时间和状态最终一致。

### 5.2 亮点二：从本地 Demo 升级为公网云服务

项目使用域名、HTTPS/WSS、Nginx、Django ASGI、PostgreSQL、Redis 和持久化文件存储构建正式云环境，使不同地点、不同网络的用户能够真实通信。

亮点价值：

- 解决 SQLite、内存 Channel Layer 和开发服务器的生产限制；
- 测试数据库、缓存、网络、证书和服务进程之间的真实集成；
- 增加监控、日志、备份、恢复和回滚等运维质量要求。

核心验收：

- 校外或不同网络设备可访问系统；
- 服务重启后账号、关系、消息和文件不丢失；
- PostgreSQL 与 Redis 不直接暴露公网；
- 至少完成一次独立环境的数据恢复演练。

### 5.3 亮点三：端到端加密（E2EE）跨平台安全通信

消息在发送端使用 ECDH、HKDF 和 AES-GCM 等机制加密，接收端在本地解密。服务端只负责认证、密文持久化和转发，不保存用户私钥、会话密钥、文件密钥明文或聊天消息明文。

本学期重点不是简单保留已有加密代码，而是验证并增强其在 Windows、Android、浏览器和公网环境中的一致性。

亮点价值：

- 将安全设计转化为可验证的接口、数据库和日志断言；
- 验证私聊发送者/接收者副本及群聊逐成员密文隔离；
- 引入密钥指纹、信任状态、密钥变化提示和设备撤销；
- 研究多设备场景下的独立设备密钥和消息分发。

核心安全边界：

1. 私钥只能保存在客户端安全存储中。
2. 服务端只能保存公钥、密钥版本、指纹、密文和必要元数据。
3. 每个私聊参与者只能访问属于自己的密文副本。
4. 每个群成员只能访问发送给自己的逐成员密文。
5. 新加入群成员不能解密加入前未向其分发的消息。
6. 被撤销设备或退出群组的设备不能获得后续消息密钥。
7. 密钥变化不能自动继承原有“已验证”信任状态。
8. AI Assistant 不得自动读取 E2EE 聊天内容和密钥。

分级目标：

- P0：Windows、Android 各自作为可信客户端安全完成 E2EE 消息收发；
- P1：同一账号多个设备使用独立密钥接收新消息，并支持设备撤销；
- P2：设计并验证经授权的历史消息安全迁移方案。

### 5.4 亮点四：弱网环境下的可靠消息机制

系统以唯一客户端消息 ID、幂等保存、连接状态机、自动重连、失败重试、遗漏消息补取和服务端时间排序解决真实网络中的消息重复、丢失和乱序问题。

亮点价值：

- 从“正常网络能发送”提升到“异常网络下结果可解释、可恢复”；
- 适合使用状态迁移、错误推测、故障注入和性能测试；
- 能够对比 HTTP fallback 与 WebSocket 的业务一致性。

核心验收：

- 重复发送不会生成重复消息；
- 断网时不显示虚假发送成功；
- 网络恢复后 30 秒内重新连接；
- 断线期间消息能够补取且顺序正确；
- 发送、送达、已读、失败等状态符合定义。

### 5.5 亮点五：覆盖完整生命周期的产业级测试

项目建立静态检查、单元测试、集成测试、端到端测试和验收测试组成的测试金字塔，并补充安全、性能、弱网、兼容性、安装和恢复测试。

测试方法包括：

- 黑盒：等价类、边界值、判定表、因果图、状态迁移、场景法和错误推测；
- 白盒：语句、分支、条件、基本路径、循环边界和异常路径覆盖；
- 专项：接口、WebSocket、E2EE、安全、性能、稳定性、兼容性和弱网测试；
- 客户端：Windows 安装/卸载、Electron E2E、Android 权限/生命周期/Appium 测试；
- 运维：部署冒烟、监控、备份、恢复和回滚测试。

首版质量目标：

| 指标 | 目标 |
| --- | --- |
| 核心后端语句覆盖率 | 不低于 85% |
| 核心后端分支覆盖率 | 不低于 75% |
| 认证、权限、幂等和加密边界覆盖率 | 目标不低于 90% |
| WebSocket 并发 | 100 个连接持续 10 分钟 |
| 消息吞吐 | 每秒 20 条，持续 10 分钟，无服务端重复记录 |
| 实时消息延迟 | 正常网络下 95% 不高于 1 秒 |
| 普通 API 延迟 | 95% 不高于 500 ms |
| 稳定性 | 连续运行 24 小时无服务崩溃 |

具体阈值允许根据云服务器配置形成经小组评审的调整记录，但最终报告必须使用实测结果。

### 5.6 亮点六：CI/CD 自动质量门禁

代码提交后自动执行格式与静态检查、Django 检查、迁移检查、自动化测试、覆盖率、依赖安全扫描、客户端构建和云端冒烟测试。

亮点价值：

- 测试成为代码合并和发布的必要条件，而不是结课前集中补写的材料；
- 每次失败都能定位到具体提交和检查阶段；
- 构建产物、测试报告和发布记录可以作为课程证据。

门禁原则：

- P0 测试失败时禁止发布；
- 覆盖率低于评审阈值时禁止直接合并；
- 发现高危漏洞或密钥泄露时立即阻断；
- 云端冒烟失败时不得继续生产发布。

### 5.7 亮点七：AI 辅助但结果可验证的软件工程过程

AI 可参与需求缺陷检查、测试点生成、边界分析、测试代码初稿、日志归纳和文档整理，但所有输出必须由成员评审并通过真实测试验证。

过程要求：

- 记录使用 AI 的任务、输入目标、输出用途和人工修改；
- AI 生成测试不得直接视为通过，必须在确定环境执行；
- 不向外部模型上传生产密钥、用户隐私和 E2EE 聊天明文；
- 对 AI 建议中发现的错误或遗漏形成反思记录。

## 六、任务拆解原则

1. 每项任务使用唯一编号，并关联需求编号、负责人和验收证据。
2. P0 任务构成最小可交付产品，优先保证端到端闭环。
3. 开发与测试并行推进，测试人员从需求阶段参与评审。
4. 每个开发任务必须包含测试任务，不能以“功能完成”代替“验收通过”。
5. 同一成员可以承担多个角色，但关键功能应交叉评审。
6. 已有功能先建立基线，迁移到新环境后必须执行回归测试。
7. 高工作量任务采用 P0/P1/P2 分级，避免因增强目标阻塞整体交付。

## 十一、任务完成定义

任何任务只有同时满足以下条件才能标记为完成：

1. 需求编号和任务范围已经确认；
2. 实现代码或配置已经提交到版本管理；
3. 代码经过至少一名非作者成员评审；
4. 对应自动化或人工测试已经执行；
5. 测试结果和必要证据已经保存；
6. 发现的阻断性缺陷已经修复或形成经批准的风险说明；
7. 相关需求、接口、部署或测试文档已经同步更新；
8. CI 中适用的 P0 质量门禁已经通过。

## 十二、风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| Windows、Android、云端同时开发导致范围过大 | 无法形成完整闭环 | 严格执行 P0/P1/P2 分级，优先完成跨端文本聊天 |
| 多设备 E2EE 复杂度过高 | 密钥丢失或安全边界错误 | P0 保证单设备安全，P1 再实现多设备新消息分发 |
| 云服务器资源有限 | 性能指标不稳定 | 先建立基线，记录配置，经评审后调整阈值 |
| 移动端 WebView 差异 | 加密、文件或布局异常 | 尽早制作 Android 技术原型并测试 Web Crypto/文件能力 |
| 网络故障难以稳定复现 | 缺陷记录不可靠 | 使用可控弱网工具，记录延迟、丢包和操作时间线 |
| 旧功能迁移后出现回归 | 核心聊天不可用 | 保留已有自动化测试，云端和客户端每次发布执行回归 |
| 覆盖率目标只追求数字 | 测试质量下降 | 同时审查分支、断言、风险和未覆盖代码，不以数量替代质量 |
| AI 输出存在错误 | 文档或测试结论失真 | 所有 AI 输出由成员评审并在真实环境执行验证 |

## 十三、实验结论

本次实验确定 iChat Pro 本学期的核心亮点为三端真实产品、公网云服务、跨平台 E2EE、弱网可靠通信、产业级测试、CI/CD 质量门禁和可验证的 AI 辅助实践。除需求与基线管理 Epic 外，实施工作按云端、Windows、Android、可靠通信、E2EE、测试、持续交付和课程材料八个 Epic 拆解，并明确了优先级、依赖、验收标准和降级策略。

后续工作以 P0 最小可交付闭环为主：先完成云服务，再实现 Windows—Android 跨端聊天，随后验证 E2EE 安全边界、可靠通信和测试质量门禁。在此基础上再逐步完成通知、多设备密钥、性能优化和自动更新等增强功能。
