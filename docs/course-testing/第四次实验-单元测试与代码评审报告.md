### 3.3 用例设计方法

单元测试不是只走正常路径，针对不同被测对象使用了对应的设计方法：

**等价类划分与边界值。** `require_base64` 的校验用例把输入划为合法 Base64、非法字符、长度不足、长度超限四类；`nonce` 固定 12 字节、`auth_tag` 固定 16 字节，测试分别覆盖恰好合法、少一字节、多一字节。文件大小上限、群成员上限（50）、同步分页上限（200）均取边界值两侧。

**状态迁移。** 消息状态机 `sending → sent → delivered → read` 用 `chat_connection.test.js` 覆盖合法迁移、非法回退、迟到 ACK 把 `failed` 恢复为 `sent`。撤回测试覆盖首次撤回成功、重复撤回返回 `already_recalled`、超时撤回返回 `recall_timeout`。

**错误推测与安全边界。** `test_t32_review.py` 专门收集评审中提出的反例：跨会话复用同一 `client_message_id`、群成员版本变更后重放、停用接收者、文件密钥覆盖非法成员、只带 holder 不带密钥材料等，每条都对应一次真实评审意见。

**并发与事务。** `ConcurrentSameIdTests` 使用 `TransactionTestCase` 触发真实的唯一约束竞态，验证内层 savepoint 回滚后外层事务仍可恢复查询，而不是用 mock 假装并发。

**生产代码直跑。** 晚 ACK 的 12 条 DOM 测试直接调用生产环境的处理函数、邻居分组函数和行移动辅助函数，作用于一个 DOM fixture，而不是重新实现一份逻辑来测自己。

### 3.5 一个真实的测试缺陷（本轮发现并修复）

单元测试本身也会出错。本轮在复核测试套件时发现一个测试污染缺陷：

`accounts/tests.py` 的 `test_avatar_crop_accepts_real_image` 会向 `/api/profile/avatar/crop/` 提交一张真实图片。该视图通过 Django 默认存储把文件写入 `settings.MEDIA_ROOT`，而测试没有覆盖 `MEDIA_ROOT`，因此**每运行一次测试套件，就往仓库的 `media/avatars/` 目录写入一个真实文件**。

由于 Django 存储在同名文件已存在时会追加随机后缀，这些文件不会互相覆盖，只会持续堆积。取证结果：

- 目录中累计 **88 个文件**，其中 **82 个是逐字节相同**的 78 字节 PNG；
- 这 82 个文件的 SHA-256 全部为 `cf98c02519d19c006f894f145aba49fa3fd603afa3a891754178ed3316a263ab`；
- 用测试输入复跑一遍视图的完整重编码流程（`convert('RGBA')` + `save(format='PNG', optimize=True)`），**输出哈希与这 82 个文件完全一致**，确认全部是测试产物；
- 数据库 `UserProfile.avatar` 只引用 3 个文件，均不在这 82 个之中。

修复方式：为该测试类增加类级临时 `MEDIA_ROOT`，并在类清理阶段删除临时目录。

```python
@classmethod
def setUpClass(cls):
    cls._media_root = Path(tempfile.mkdtemp(prefix='ichat-test-media-'))
    cls.enterClassContext(override_settings(MEDIA_ROOT=cls._media_root))
    cls.addClassCleanup(shutil.rmtree, cls._media_root, ignore_errors=True)
    super().setUpClass()
```

使用 `Path` 而非 `str`，是因为 `chat/views.py` 中存在 `MEDIA_ROOT / 'uploads' / ...` 的路径拼接用法，覆盖成字符串会破坏该写法。

验证：跑完整套件前后 `media/avatars/` 均为 6 个文件，临时目录无残留。清理时只删除哈希与被测输出逐字节一致的 82 个文件，数据库引用的 3 个头像全部保留并验证仍可解析。

这条缺陷的意义在于：**测试用例"通过"不代表测试没有副作用**。原先 404 条全绿，但绿色之下每次都在污染工作区。

## 四、代码评审过程

### 4.1 评审流程

项目采用 `Issue → 独立分支 → 本地验证 → Pull Request → 他人评审 → 合并 → 验收证据` 的流程，`main` 保持可演示、可测试。完整协作规则见 [GitHub 协作开发指南](../GitHub协作开发指南.md)。

| 阶段 | 工具 | 落地产物 |
| --- | --- | --- |
| 任务与范围 | GitHub Issues | 78 项 `P4 Txx` / `P4 Test Txx` 任务卡 |
| 分支与提交 | Git | `feature/`、`fix/`、`test/`、`docs/` 前缀分支 |
| 评审载体 | GitHub Pull Request | PR 模板 + 评审意见 + 修改提交 |
| 自动检查 | GitHub Actions | test / integration / javascript / windows-installer |
| 评审清单 | `代码规范、版本管理与测试工具说明.md` §3.6 | 6 类必查项 |

### 4.2 评审清单

仓库规定每次评审至少检查：

1. 是否只实现了 Issue 约定的范围；
2. 是否正确处理权限、异常、空值、重复请求和并发；
3. 是否破坏旧客户端、旧数据或既有聊天功能；
4. 是否新增或更新了必要测试；
5. 是否存在明文密钥、隐私日志、注入、越权或不安全文件访问；
6. 测试证据是否可复现，文档和配置是否同步更新。

PR 模板另有"文档与证据同步"三项强制勾选，明确要求"未运行的检查不得写成通过""CI 全绿不代替原生验收"。

### 4.5 评审发现并修复的缺陷

评审产出的不是"意见清单"，而是可复现的缺陷与对应回归用例。以下是已记录闭环的四例：

**缺陷 1：晚 ACK 错行（严重度：高）**

- **现象**：补取把接收到的消息插到延迟发送的消息之前时，按新数组下标去改旧 DOM 顺序，会替换掉一条无关的行。基线复现为数组 ID `[43,44,45]` 而 DOM 为 `[45,44,45]`。
- **评审发现路径**：T33/T20 多轮评审逐轮核对行身份定位方式。
- **修复**：ACK 处理改为定位并重标原临时行，用服务端时间更新数组，移动完整行后再按新旧两个位置重建分组；找不到行或后继行时整体重渲染。
- **回归用例**：`message_accepted.test.js` 12 条，覆盖尾部/前部/中部、时间戳并列、重复 ACK、选中身份、缺失行/旧行/系统行、AI 容器隔离。
- **真实环境复验**：真实桌面断网发送 + 第二浏览器发两条消息 + 延迟 3 秒重发，9.241 秒恢复，数组与 DOM 均为 `[46,47,48,49]`，刷新无重复。

**缺陷 2：公钥版本被最新缓存版本替代（严重度：高，属加密边界）**

- **现象**：显式指定公钥版本时，被最新缓存版本替代；密钥轮换后既有加密测试暴露回归。
- **修复**：显式版本必须精确命中缓存，无版本离线发送保留最新密钥回退。
- **回归用例**：`public_key_cache.test.js` 2 条，覆盖私聊与群聊两个模块。

**缺陷 3：卸载登记前缀匹配误删（严重度：高，涉及用户数据）**

- **现象**：卸载登记只按安装目录前缀匹配，可能误删路径相似的另一次安装；全机卸载可能选错用户数据目录。
- **修复**：改为引号感知的精确匹配，按 UninstallString 位置限定清理范围。
- **验证**：24 项真实 NSIS 宏隔离断言，覆盖路径/参数边界、独立登记、是/否/静默分支和安装模式。

**缺陷 4：通知预览泄露与布局回归（严重度：中）**

- **现象**：通知设置未就绪时可泄露消息预览；未知会话未查明静音即通知；内嵌设置开关引起侧栏滚动约 695px 并挤压搜索头部。
- **修复**：通知门控按"设置未就绪即关闭"处理，未知会话先读元数据查静音；布局修复重排侧栏 flex 尺寸与聊天顶部定位。
- **验证**：通知三套回归接入 CI；Chromium 布局 36 项，同套用例在修复前的基线上失败——这条"基线失败、修复后通过"的记录是回归测试有效性的关键证据。

### 4.6 评审纪律

仓库明确规定了几条防止评审流于形式的约束：

- **禁止直接向稳定分支提交未经测试的功能**；
- **禁止通过删除或跳过失败测试来"修复"流水线**；
- **禁止伪造测试记录、覆盖率、AI 输出或验收截图**；
- **禁止仅凭 AI 生成结果合并代码**，所有结果必须经人工审查和可复现验证；
- 关键安全或 E2EE 改动应由**非作者成员**复核；
- "代码存在""测试已编写""本地能打开页面"**不能**当作跨端安装与公网验收通过。

最后一条在本轮任务中再次被验证：测试套件 404 条全绿，但 `media/avatars/` 仍在被持续污染——**CI 绿不等于没有问题**。

## 五、当前不足（如实记录）

1. **没有覆盖率数据**。`coverage.py` 在工具清单中列为"计划接入"，尚未实际执行，因此本报告不提供语句/分支覆盖率数字。需求文档中 85%/75%/90% 的覆盖率目标是**目标值而非实测值**。
2. **没有静态检查与安全扫描**。Ruff、Bandit、pip-audit/npm audit 均未接入，格式与安全扫描未闭环。
3. **CI 未强制阻断合并**。GitHub `main` 未配置 `required_status_checks`，rulesets 为空。现有四个 job 会运行并通过，但"测试失败禁止合并"目前是**协作约定，不是技术强制**。
4. **测试分布不均**。`accounts.tests` 单文件 127 条、`test_core.py` 80 条，两个文件占全部用例的一半以上；而 Android 相关测试为 0，因为 Android 工程尚未开始。
5. **缺少评估测试质量的指标**。本轮修复的测试污染缺陷说明：用例数量、"全绿"结果都不能说明测试本身是健康的，项目目前没有变异测试、测试副作用检查等手段。
6. **评审依赖单人环境**。仓库提交者以单一账号为主，多人评审更多体现在流程要求而非多个独立评审人的记录上。

## 六、实验结论

1. 后端 404 条、前端 62 条、桌面 36+22+24 项测试在本轮全部实际执行并通过，`check` 与迁移一致性检查无问题。
2. 单元测试按模型、服务层、HTTP、WebSocket、协议、补取、E2EE、客户端状态机、桌面和运维分层设计，使用了等价类、边界值、状态迁移、错误推测和真实并发等不同方法，不是单一模板的重复。
3. 代码评审有真实载体（118 个已合并 PR）、真实强度（28 次 review round，最高 10 轮）和真实产出（可复现缺陷 + 对应回归用例 + 修复后验证）。
4. 本轮发现并修复了一个**测试自身的缺陷**：头像测试长期向仓库 `media/` 目录写入文件，累计 82 个可证明的测试产物，已通过临时 `MEDIA_ROOT` 隔离修复并清理。
5. 项目的测试体系仍有明显缺口：无覆盖率、无静态扫描、CI 不强制阻断合并、Android 无测试。这些是后续实验需要推进的内容，本报告不将其记为已完成。
